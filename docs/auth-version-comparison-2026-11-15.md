# Сравнение авторизации и регистрации agy 1.4.5 и 1.5.9

Дата: 2026-11-15.

## Цель и итог

Сравнить прежнюю рабочую версию 1.4.5 с прежним патчем и новую 1.5.9: OAuth, параметры `loadCodeAssist`, параметры `onboardUser` и текущие ответы сервера. Пользователь подтвердил, что прежней рабочей версией была именно 1.4.5.

В проверенных полях различий не найдено. Обе версии используют один consumer OAuth client ID и одинаковые scopes. Обе отправляют одинаковые JSON-параметры `loadCodeAssist` и `onboardUser` на один origin. Сейчас сервер одинаково отклоняет бесплатную регистрацию обеих версий, включая старую 1.4.5. Переход на 1.5.9 сам по себе не объясняет отказ изменением этих параметров.

В описанном сравнении реальный ответ модели не получен: после пропуска локальных остановок обе версии получают `403 #3501` при генерации и нулевой расход токенов. Последующий этап выявил [рабочий AICode-путь бесплатного ответа](aicode-free-access-working-path-2026-11-15.md); он не использует отклоняемый `onboardUser` и требует исправления устаревшего имени experience в 1.5.9.

## Условия сравнения

Использованы отдельные копии бинарников, одинаковый локальный прокси, текущая сохранённая OAuth-сессия и отдельные чистые профили. Cloud/ADC-переменные удалены из окружения дочерних процессов, `useAiCredits=false`, MCP-конфигурация пуста. Автообновление отключено через `AGY_CLI_DISABLE_AUTO_UPDATE=true`.

Для исходного контроля обе копии содержат прежние CLI gate и Manager gate. Обе останавливаются до генерации с `Eligibility check failed`. Для сопоставления `onboardUser` и генерации в отдельные экспериментальные копии добавлены одинаковые по назначению пропуски трёх локальных остановок: в print mode, отправке сообщения и возврате ошибки eligibility перед бесплатной регистрацией. Серверные ответы, OAuth-токены и параметры тарифа не подменяются. Экспериментальные копии не устанавливались, изменения не добавлялись в продуктовый патчер.

Метод наблюдения: Win64 Debug API с аппаратными точками исполнения в собственном дочернем процессе. Сняты выбранные поля OAuth config, сериализованные JSON-запросы только двух исследуемых методов, их ответы с редактированием прочих строк, host/path и HTTP-статусы. Заголовки авторизации и токены не читаются. У окончательных используемых трасс список `observation_errors` пуст.

Сравнение JSON семантическое: поля и значения. Полная побайтовая идентичность HTTP-заголовков, TLS и framing не проверялась. Изменение версии User-Agent отдельно не измерялось.

## OAuth

В обеих версиях при текущем входе наблюдался результат нативной `cli/backend/auth.oauthConfigFor`:

| Параметр | 1.4.5 | 1.5.9 |
| --- | --- | --- |
| Consumer client ID | `1071006060591-tmhssin2h21lcre235vtolojh4g403ep.apps.googleusercontent.com` | Совпадает |
| Authorization endpoint | `https://accounts.google.com/o/oauth2/auth` | Совпадает |
| Token endpoint | `https://oauth2.googleapis.com/token` | Совпадает |
| Настроенные scopes | Семь scopes ниже | Совпадают |
| Consumer client secret из бинарника | Проверено только равенство констант | Совпадает; значение не выводилось |

Настроенные scopes:

```text
openid
https://www.googleapis.com/auth/userinfo.email
https://www.googleapis.com/auth/userinfo.profile
https://www.googleapis.com/auth/cloud-platform
https://www.googleapis.com/auth/cclog
https://www.googleapis.com/auth/experimentsandconfigs
https://www.googleapis.com/auth/aicode
```

Это scopes конфигурации клиента, а не новый независимый замер фактически выданных прав старого токена. В первоначальном сравнении новый code exchange не выполнялся: использовалась сохранённая сессия. Последующая [проверка свежего OAuth самой 1.4.5](fresh-oauth-1.4.5-check-2026-11-15.md) подтвердила новый token HTTP 200, вход на том же аккаунте и те же отказы регистрации и генерации. Пустой `redirect_uri` в конфигурации тихой авторизации не означает ошибочный callback; интерактивный путь устанавливает callback отдельно.

Статически сопоставлены пять функций CLI: `StartInteractive`, `getOauthParams`, `getScopesByAuthMethod`, `getOAuthConfig`, `oauthConfigFor`. После нормализации адресов функций и relocations их структуры инструкций совпадают. Нормализация адресов сама по себе не доказывает равенства всех данных; client ID, endpoint и scopes дополнительно подтверждены динамически.

Обе интерактивные реализации задают callback `https://antigravity.google/oauth-callback`, PKCE `S256` и `prompt=consent`. У нового ACP-входа URL также фактически содержит `access_type=offline`, `response_type=code` и эти параметры. Свежий браузерный вход 1.4.5 выполнен последующим отдельным контролем, указанным выше. В 1.4.5 нет ACP-подкоманды; её интерактивный вход реализован обычным CLI. Это различие поверхности входа, а не обнаруженное изменение consumer client ID или scopes.

Существующая ветвь `gcp` с другим client ID присутствует в обеих версиях. Текущий наблюдаемый выбор соответствует consumer; переключение на GCP в данном сравнении не выполнялось.

## `loadCodeAssist`

Обе версии фактически выбирают:

```text
POST https://daily-cloudcode-pa.googleapis.com/v1internal:loadCodeAssist
```

Полный набор JSON-полей исследуемого запроса совпадает:

```json
{
  "metadata": {
    "ideType": "ANTIGRAVITY"
  }
}
```

В обеих версиях в этом запросе отсутствуют `cloudaicompanionProject`, `tierId`, `platform`, `pluginType` и поля версии. Значение `ideType` не сменилось на другое после обновления.

Обе получают HTTP 200 с одинаковыми проверенными полями:

- `allowedTiers`: `standard-tier`, имя `Antigravity`, `isDefault=true`, `usesGcpTos=true`, `userDefinedCloudaicompanionProject=true`;
- `ineligibleTiers`: `tierId=free-tier`, `reasonCode=UNSUPPORTED_LOCATION`;
- `currentTier`, `paidTier` и project не выданы.

Наличие `standard-tier` среди вариантов не является назначенной аккаунту лицензией. Ответы сравнивались после одинакового редактирования строк описаний и иных несущественных полей. Отсутствие текущего тарифа и отказ free-tier сохраняются в обеих версиях.

## `onboardUser`

В исходном контроле обе версии прекращают проверку до этого вызова. После экспериментального пропуска локального возврата ошибки обе выполняют собственный штатный запрос:

```text
POST https://daily-cloudcode-pa.googleapis.com/v1internal:onboardUser
```

Его полный набор JSON-полей совпадает:

```json
{
  "tierId": "free-tier",
  "metadata": {
    "ideType": "ANTIGRAVITY"
  }
}
```

Таким образом, старая версия тоже запрашивает именно бесплатный тариф; project и идентификатор платного тарифа в её запросе не появились.

Обе получают:

```json
{
  "code": 403,
  "status": "PERMISSION_DENIED",
  "reason": "UNSUPPORTED_LOCATION",
  "domain": "cloudaicompanion.googleapis.com",
  "error_number": "1008"
}
```

Последующий `POST /v1internal:streamGenerateContent` обеих версий получает HTTP 403 и финальное сообщение `#3501`. Это тот же серверный отказ, источник которого отдельно установлен в [сетевом отчёте](native-http-3501-trace-2026-11-15.md).

## Что делал прежний патч

Исходная резервная копия 1.4.5 имеет SHA-256 `d191b2e423c8c5a96ffba84699dd5f52f4eec0e74bb457e8d5f755dc55528f9d`. Между ней и сохранённым пропатченным 1.4.5 изменены только девять байтов в двух окнах проверок:

- Manager gate: окно `0x255674a`, `80 78 08 00 74 3b` → `c6 40 08 01 90 90`; один байт совпадает с исходным, поэтому фактически изменены пять байтов;
- CLI gate: окно `0x2d698c9`, `80 78 08 00` → `48 85 c0 90`.

Прежний патч не менял client ID, scopes, endpoint или metadata. Он менял обработку локального результата проверки и флага авторизации. Поэтому его прежняя работоспособность совместима с тем, что сервер тогда уже разрешал запросы аккаунта, а приложение останавливало пользователя локально.

## Историческое объяснение и UNKNOWN

Проверены сохранённые октябрьские CLI-журналы: 282 файла. В 280 найдены записи успешной OAuth-аутентификации; идентичность в них совпадает с текущим сравнительным запуском. Персональные значения не экспортировались. Это не подтверждает, что каждый из этих запусков успешно обращался к модели, но не даёт оснований объяснять изменение случайным выбором другого аккаунта.

В этих журналах не найдены сохранённые payload с `currentTier`, `paidTier`, `allowedTiers`, `ineligibleTiers` или `cloudaicompanionProject`. Они не позволяют установить серверный тариф в момент прежнего успеха. Наличие строк статистики генерации само по себе не восстанавливает лицензионное состояние.

Подтверждено:

1. Старый 1.4.5 с прежним патчем сегодня тоже не получает бесплатного ответа.
2. Публичная OAuth-конфигурация и исследуемые параметры запросов не объясняют различие между версиями: они совпадают.
3. Текущий серверный отказ относится к выдаче `free-tier`, а не только к локальному UI.

С учётом сообщённой пользователем утраты подписки с данными согласуется следующий сценарий: раньше серверное право обеспечивалось действовавшим доступом аккаунта, а патч снимал локальную остановку; после утраты этого права понадобилась регистрация бесплатного тарифа, которую сервер отклоняет. Это гипотеза, не восстановленный факт о прежнем `paidTier`.

Альтернативное объяснение — изменение серверных правил или серверного состояния eligibility. Разделить эти причины без исторического ответа сервера о тарифе невозможно. Утверждение «обновление изменило OAuth или параметры регистрации и тем самым сломало доступ» выполненное сравнение не подтвердило. Утверждение «старый патч обеспечивал именно free-tier независимо от подписки» этим сравнением также не проверено за прошлый период.
