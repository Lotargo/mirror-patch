# Сетевой источник 403 #3501 и регистрация бесплатного тарифа

Дата: 2026-11-15.

## Цель и результат

Найти конкретный сетевой запрос, который завершает нативную генерацию ошибкой `403 #3501`, проверить выбор маршрута и возможность регистрации бесплатного тарифа после корректного OAuth.

Источник ошибки установлен: `POST /v1internal:streamGenerateContent` действительно получает HTTP 403 от Cloud Code. Его тело содержит `SUBSCRIPTION_REQUIRED`, `error_number=1001` и сообщение `#3501`. Это отдельное подтверждение для генерации, а не перенос ошибки фонового запроса квот.

Реального ответа модели не получено: CLI завершает один ход с пустым ответом, нулевым расходом токенов и кодом выхода 3. Дополнительная попытка штатной регистрации `free-tier` отклонена production-сервером: HTTP 403, `UNSUPPORTED_LOCATION`, `error_number=1008`.

## Метод и границы наблюдения

Использован нативный CLI 1.5.9 в отдельной тестовой копии с уже описанными двумя экспериментальными обходами локальных остановок. Изолированный профиль содержит пустую конфигурацию MCP; рабочий каталог теста пуст. В запросе указано ответить `SERVICE_OK` и не вызывать инструменты. Сохранённый OAuth используется штатным клиентом. Переменные облачного проекта удалены из окружения дочернего процесса; используется тот же локальный прокси, что и в предыдущих успешных проверках авторизации.

Наблюдатель `native_hw_http_trace.py` запускает только свой дочерний процесс через Win64 Debug API и аппаратные точки исполнения. Он не внедряет DLL и не меняет выполняемый код. Считываются метод, host/path без query, HTTP-статус, два поля маршрутизации protobuf и выбранные поля JSON-ошибки. Заголовки авторизации, содержимое промпта и хранилище токенов не читаются. Тело ошибки читается ограниченно, после того как его уже прочёл сам клиент; сохраняются только классификация ошибки и сообщение.

Адреса функций привязаны к проверенной сборке. Они не являются универсальным профилем других версий. Успешные трассы завершились штатным результатом CLI; список `observation_errors` пуст. Неудачные ранние эксперименты с Frida не использованы как доказательство поведения сервиса.

## Точный вызов генерации

| Контроль | Сетевой запрос | Ответ |
| --- | --- | --- |
| Штатный выбор | `POST https://daily-cloudcode-pa.googleapis.com/v1internal:streamGenerateContent` | HTTP 403 |
| Production origin через `CLOUD_CODE_URL` | `POST https://cloudcode-pa.googleapis.com/v1internal:streamGenerateContent` | HTTP 403 |
| Альтернативный встроенный режим `USE_AICODE=true` | `POST https://aicode.googleapis.com/v1alpha:streamGenerateContent` | HTTP 404 `NOT_FOUND` |

У этих ответов не было ошибки транспорта. Успех `aicode.googleapis.com/v1alpha:fetchConfig` не означал доступность генерации через AICode: отдельный контроль фактического inference дал 404. Предположение о том, что достаточно дождаться конфигурации и поменять маршрут, не подтвердилось.

В штатном запуске аппаратная точка после `useAICodePredictionFlow` показала `false`. Перед `marshalCCPARequest` зафиксированы:

```json
{
  "project_present": false,
  "model": "gemini-3.8-flash-high"
}
```

Это фактический upstream ID модели в этом запуске. Более ранний контроль с `gemini-3-flash` не применим: текущий нативный CLI отклоняет такой ID до запроса генерации.

Выбранные поля ответа именно на `streamGenerateContent`:

```json
{
  "code": 403,
  "status": "PERMISSION_DENIED",
  "reason": "SUBSCRIPTION_REQUIRED",
  "domain": "cloudaicompanion.googleapis.com",
  "error_number": "1001"
}
```

Сообщение ответа: `You do not have a valid license of this product ... (#3501)`.

## Проверка назначения бесплатного тарифа

В нативном процессе после успешного `loadCodeAssist` прочитаны только поля тарифа и признаки project: `currentTier=null`, `paidTier=null`, project отсутствует, один элемент `ineligibleTiers`. Независимый повтор `GetLoadCodeAssist` в pristine Hub с CLI-хранилищем подтвердил `free-tier / UNSUPPORTED_LOCATION`; в `allowedTiers` указан `standard-tier`. Наличие варианта в `allowedTiers` не доказывает назначение действующего тарифа.

Наблюдение за входами функций показало вызов `ValidateAndOnboardAccount`, но отсутствие вызова `OnboardUser` в обычном тесте. Статический разбор подтвердил: функция возвращает ошибку eligibility до штатной регистрации `free-tier`.

Для проверки этой развилки создана ещё одна отдельная экспериментальная копия. В ней пропущен один локальный переход к возврату уже известной ошибки eligibility. OAuth, тело `loadCodeAssist`, серверные тарифы и идентификаторы не подменялись. Клиенту позволено выполнить его собственный запрос регистрации бесплатного тарифа. Эта правка не добавлена в production-патчер и не установлена пользователю.

Манифест копии:

- источник SHA-256: `401c13db7f951e63852e1d2e9f649e520df1690f443d22de9c5ac6ac22f364d7`;
- результат SHA-256: `be1226dec66bde83cf6198674fe9b252182c05c0eb7fd84dce4424ac73a49e56`;
- единственная дополнительная замена: VA `0x142b89e85`, file offset `0x2b89485`, `0f85f0000000` → `909090909090`.

Наблюдатель прочитал аргумент нативной функции: `requested_tier=free-tier`. Сетевые результаты:

| Запрос | Daily | Production |
| --- | --- | --- |
| `POST /v1internal:onboardUser`, штатный `free-tier` | HTTP 403 | HTTP 403 |
| Последующий `POST /v1internal:streamGenerateContent` | HTTP 403 | HTTP 403 |

Из тела production-ответа именно на `onboardUser`:

```json
{
  "code": 403,
  "status": "PERMISSION_DENIED",
  "reason": "UNSUPPORTED_LOCATION",
  "domain": "cloudaicompanion.googleapis.com",
  "error_number": "1008"
}
```

Серверное сообщение указывает, что текущему аккаунту недоступен Gemini Code Assist for individuals. Конкретные персональные или географические данные в отчёт не включены.

## Объяснение и оставшаяся неопределённость

Наблюдаемая цепочка согласуется с отсутствием назначенного бесплатного доступа: сервер не выдаёт текущий тариф, отклоняет регистрацию `free-tier`, затем отклоняет генерацию общим сообщением об отсутствии лицензии. Слово `SUBSCRIPTION_REQUIRED` само по себе не доказывает, что бесплатный режим отменён или что клиент притворился Pro. Здесь отдельно проверен запрос именно бесплатной регистрации, и он тоже отклонён сервером.

Предыдущая гипотеза об устаревшем `GetUserStatus=Pro` не получила подтверждения: в этой сборке отображаемый PlanStatus строится из общей константы, как описано в `free-tier-license-diagnosis-2026-11-15.md`. Смена endpoint на два проверенных альтернативных маршрута доступа не дала.

Это не устанавливает внутреннюю реализацию серверного лицензирования и не объясняет историческую причину работоспособности старого патча. Возможное влияние ранее выданного платного доступа или изменений сервера остаётся UNKNOWN. Проверенные результаты не доказывают отсутствие любых других клиентских проблем, но устанавливают самостоятельный серверный отказ регистрации бесплатного тарифа в текущем состоянии аккаунта.

Для проверенного здесь пути Cloud Code успешная бесплатная регистрация оставалась условием доступа. Этот вывод нельзя распространять на все встроенные API: последующий этап нашёл [рабочую личную ветку AICode](aicode-free-access-working-path-2026-11-15.md), которая получает настоящий `free-tier` из `fetchLicenses` и не требует прежнего `onboardUser`. После исправления устаревшего имени experience эта ветка дала HTTP 200 и реальный ответ модели. Повтор OAuth сам по себе отказ Cloud Code не устранил.
