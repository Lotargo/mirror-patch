# Диагностика бесплатного доступа и ошибки 403 #3501

Дата: 2026-11-15.

## Цель и текущий результат

Дополнение следующей проверки: [нативный CLI после пропуска двух локальных отказов](native-cli-local-gates-check-2026-11-15.md). Она отдельно подтверждает существование локальных барьеров, отправку сообщения штатным CLI и сохраняющуюся ошибку исполнения. Точный URL финального HTTP 403 остаётся не установлен.

Проверить получение реального ответа от Antigravity CLI с личным Google-аккаунтом без платной подписки и определить, вызван ли отказ устаревшим статусом Pro, режимом авторизации, endpoint или серверной доступностью бесплатного тарифа.

Ответ модели пока не получен. Установлено, что свежий OAuth работает, но текущий серверный ответ явно исключает `free-tier` с причиной `UNSUPPORTED_LOCATION`. Надпись `Pro` в локальном `GetUserStatus` происходит из встроенного в официальный бинарник объекта, а не доказывает сохранение прежней подписки. Проверенные настройки режима, Cloud-окружения, модели и endpoint не устранили отказ.

## Бесплатный доступ предусмотрен продуктом

Официальные [Plans](https://antigravity.google/docs/plans) описывают недельную квоту для пользователей без Pro/Ultra и доступ к CLI. [FAQ](https://antigravity.google/docs/faq) прямо допускает личные Google-аккаунты на бесплатном тарифе, но связывает доступность со страной, ассоциированной с аккаунтом. Отсутствие подписки само по себе не объясняет невозможность любого ответа.

## Свежий серверный ответ

Проверена неизменённая официальная сборка agy 1.5.9:

`SHA-256 8803c289cac04d6e53f2211592d9981c2d5760bc0d9b4a7f222ef6ecc7abb38a`.

Для тестового процесса убраны Cloud-переменные окружения. Системные настройки и установленные бинарники не менялись. Сетевой транспорт использовал уже работающий локальный прокси. Новый Hub-процесс исключает повторное использование его прежнего кеша в памяти.

`GetLoadCodeAssist` вернул HTTP 200:

```json
{
  "allowedTiers": [
    {
      "id": "standard-tier",
      "name": "Antigravity",
      "isDefault": true,
      "usesGcpTos": true
    }
  ],
  "ineligibleTiers": [
    {
      "tierId": "free-tier",
      "reasonCode": "UNSUPPORTED_LOCATION"
    }
  ]
}
```

Сервер также пояснил, что Antigravity недоступен аккаунту по местоположению. Это конкретный отказ бесплатному тарифу; он получен до успешной генерации. Наличие `standard-tier` в `allowedTiers` не означает, что действующая лицензия на него назначена аккаунту. В проверенном ответе нет `currentTier`.

Отдельный запрос `retrieveUserQuotaSummary` получил HTTP 403, `PERMISSION_DENIED`, причину `SUBSCRIPTION_REQUIRED` и сообщение `#3501`. Это другой вызов API. Один номер #3501 не устанавливает, что клиент запросил режим Pro.

## Откуда берётся Pro

Статический анализ выполнен на той же чистой сборке, без патчей:

1. `UserStatus.GetPlanStatus` читает поле объекта по смещению `0xa0`.
2. `codeassistclient.buildUserStatus` заполняет это поле из общего указателя `0x14d7dbf70` по адресам кода `0x14279db94`–`0x14279dbac`.
3. `constants.init` связывает этот `PlanStatus` с общим `PlanInfo`, загружаемым через `0x14d7dbf68`, по адресам кода `0x140dd5013`–`0x140dd5036`.
4. Соответствующий объект `PlanInfo` уже присутствует в файле официального бинарника по VA `0x14d8687a8`. В нём находятся строка `Pro` и числовое значение `teamsTier=2`, соответствующее наблюдаемому `TEAMS_TIER_PRO`.

Следовательно, именно наблюдаемая надпись `GetUserStatus.planStatus.planInfo.planName=Pro` не является доказательством устаревшего пользовательского кеша подписки. Она подставляется из общей структуры клиента. Предыдущее предположение об её возможном происхождении из старой подписки уточнено этим анализом.

В проверенной схеме исходящего `RetrieveUserQuotaSummaryRequest` есть поле `project`, но нет поля Pro/Free или `planName`. Функция `fetchRetrieveUserQuotaSummary` получает project через `getCAICProject` и создаёт этот запрос. `getCAICProject` использует ответ LoadCodeAssist либо предусмотренный auth-provider override, а не строку Pro из `GetUserStatus`. Гипотеза о непосредственном выборе платного запроса из-за этой строки не подтвердилась.

Это не утверждение об отсутствии любой иной метаинформации в сохранённых credentials: значения чувствительных токенов не экспортировались, а все возможные внутренние решения сервера неизвестны. Для текущего отказа имеется независимый прямой ответ о недоступности `free-tier`.

## Контроль режима, окружения, endpoint и модели

| Гипотеза | Выполненная проверка | Результат |
| --- | --- | --- |
| Используется business вместо personal | Последний успешный ACP OAuth имеет `methodId=oauth-personal`; проверены ветви `CLIAuthProvider.ResolveAuthMode` и `SetHTTPHeaders` | Само наличие Pro в отображаемом статусе не выбирает business-режим |
| Режим меняет Cloud-переменная | В отдельном процессе удалена присутствовавшая `GOOGLE_CLOUD_PROJECT`; другие Cloud/ADC-переменные также исключались при наличии | Тот же отказ бесплатному тарифу |
| Ошибочен daily endpoint | Чистая сборка проверена с обычным `daily-cloudcode-pa.googleapis.com` и с процессным override на встроенный `cloudcode-pa.googleapis.com` | Оба запуска завершились тем же отказом по доступности; смена origin подтверждена журналами |
| Выбрана исключительно платная модель | В раннем тесте указан `gemini-3-flash` | Отказ eligibility возник до валидации модели; последующая проверка показала, что этот идентификатор текущим CLI не принимается. Нативные контрольные тесты затем выполнены с текущей моделью по умолчанию Gemini 3.8 Flash (Medium) |
| Ошибку создаёт патч | Повторён запрос чистым бинарником | Чистый CLI показывает полную причину отказа; прежний CLI-патч скрывает её текст, но не открывает сервис |
| OAuth не состоялся | Штатный свежий ACP OAuth завершился кодом 0; последующие журналы содержат `silent auth succeeded` | Получение токена подтверждено; разрешение на бесплатный сервис не предоставлено |

И у обычного endpoint, и у альтернативного подтверждён реальный исходящий origin. Постоянный endpoint override не сохранялся.

## Объяснение ранее работавшего доступа

По сообщению пользователя, до обновления и прекращения подписки ответы приходили. Возможное объяснение: платная подписка предоставляла отдельное серверное право доступа, тогда как после её прекращения аккаунт должен был перейти на бесплатный тариф и столкнулся с его проверкой доступности. Это согласуется с текущими наблюдениями, но не является доказанным восстановлением прежнего серверного состояния.

Исследованные локальные патчи не создают серверную подписку или бесплатную квоту. Они меняют клиентскую интерпретацию результата eligibility/авторизации. Поэтому работа такого патча на аккаунте с подпиской не доказывает его эффективность после перехода на free.

## Что необходимо для следующей проверки

Официальный [FAQ](https://antigravity.google/docs/faq#what-is-google-antigravitys-geographical-availability) предлагает проверить страну на [Google Terms of Service](https://policies.google.com/terms). Если ассоциация аккаунта неверна, FAQ ссылается на штатный запрос её исправления. Фактическая страна аккаунта в рамках этой проверки не установлена и в отчёт не включается.

- Если аккаунт ассоциирован с поддерживаемой страной, текущий `UNSUPPORTED_LOCATION` требует разбора серверной классификации аккаунта. Исправление на стороне Google нельзя подтвердить изменением локальной строки Pro.
- Пока сервер продолжает исключать `free-tier`, получение реального ответа на этом аккаунте не достигнуто. Покупка подписки не предлагалась как обязательное условие бесплатного доступа.
- Полный IDE-сеанс и все серверные условия выдачи entitlement остаются вне подтверждённого результата.
