# Свежий OAuth через agy 1.4.5 и повтор бесплатной регистрации

Дата: 2026-11-15.

## Цель и результат

Исключить влияние сессии, полученной через новую версию: завершить новый браузерный OAuth именно штатным кодом старой 1.4.5, затем проверить восстановление авторизации после перезапуска, регистрацию `free-tier` и генерацию.

Свежий OAuth 1.4.5 успешно завершён на том же аккаунте, что использовался в предыдущем сравнении. Google token endpoint вернул HTTP 200; нативная `oauth2.Config.Exchange` вернула новый объект токена без ошибки. После выхода из интерактивного процесса два новых процесса 1.4.5 восстановили вход из keyring.

Отказы сервиса сохранились:

| Этап | Фактический результат |
| --- | --- |
| Новый code exchange самой 1.4.5 | `POST https://oauth2.googleapis.com/token` → HTTP 200 |
| Восстановление входа после перезапуска 1.4.5 | Успешная тихая авторизация через keyring, тот же аккаунт |
| `loadCodeAssist` | HTTP 200, `free-tier` указан в `ineligibleTiers` с `UNSUPPORTED_LOCATION` |
| `onboardUser`, `tierId=free-tier` | HTTP 403, `UNSUPPORTED_LOCATION`, error 1008 |
| `streamGenerateContent` | HTTP 403, финальное сообщение `#3501` |
| Ответ модели | Пустой; один ход, ноль токенов; CLI exit 3 |

Для этого аккаунта источник сессии 1.5.9 не объясняет отказ: после выхода и получения новой сессии самой 1.4.5 наблюдается тот же результат. Успешная генерация в этом пути не достигнута. Последующее исследование получило [реальный бесплатный ответ через AICode в 1.5.9](aicode-free-access-working-path-2026-11-15.md) с использованием сохранённого здесь свежего входа. Историческая причина прежней работоспособности патча по-прежнему не установлена.

## Как обеспечена свежесть входа

1. Запущена отдельная копия 1.4.5 с прежними CLI gate и Manager gate, SHA-256 `08168b9f2a124944c78f50261d05a4fdbe372c6f2c1935b9e09c3ab004ab0238`.
2. В обычном интерактивном CLI выполнен штатный `/logout`, затем выбран `Google OAuth`. ACP и код 1.5.9 для входа не использовались.
3. Сам старый CLI сгенерировал новый state и PKCE verifier, открыл браузер и ожидал код. Пользователь завершил вход, код передан в ожидающий процесс 1.4.5.
4. Аппаратная точка исполнения зарегистрировала вызов `oauth2.Config.Exchange`, реальный запрос к `/token`, HTTP 200 и возврат токена без ошибки. Это новый обмен authorization code, а не только использование ранее сохранённого access token.
5. Интерактивный процесс завершён штатной `/exit`, exit 0. После этого запущены отдельные процессы 1.4.5. Их журналы содержат `ChainedAuth: authenticated via keyring` и `Print mode: silent auth succeeded`.
6. Идентичность в обоих повторных запусках совпала с предыдущим сравнением. Персональные значения проверены локально и не экспортировались.

Первая попытка свежего входа оказалась выполнена на другом аккаунте. Она выявлена сравнением идентичности; пользователь выбрал повтор на прежнем аккаунте. Её артефакты сохранены отдельно в `fresh-old-attempt-1/` и не использованы как контроль того же аккаунта.

Код вводился в отдельное окно с явной кнопкой вставки. Одноразовый локальный bridge держал код только в оперативной памяти и передал его в стандартный ввод ожидающего CLI. Файл управления содержал только порт и случайный ключ bridge, был удалён после передачи. Коды OAuth и значения токенов в отчёт и диагностические JSON не включены.

## Наблюдаемая OAuth-конфигурация

В свежем вызове `Config.Exchange`:

- consumer client ID: `1071006060591-tmhssin2h21lcre235vtolojh4g403ep.apps.googleusercontent.com`;
- token endpoint: `https://oauth2.googleapis.com/token`;
- redirect URI: `https://antigravity.google/oauth-callback`;
- настроены те же семь scopes: `openid`, `userinfo.email`, `userinfo.profile`, `cloud-platform`, `cclog`, `experimentsandconfigs`, `aicode` с соответствующими полными Google API URI.

Значения authorization code, verifier, access token и refresh token наблюдатель не читал. Отдельный список фактически выданных scopes из тела токена не извлекался; приведены scopes конфигурации запроса. Ошибки `invalid_grant` или `ACCESS_TOKEN_SCOPE_INSUFFICIENT` в проверенном результате не наблюдались.

## Повтор регистрации и генерации

Обычная копия с прежними двумя патчами после успешной тихой авторизации снова остановилась на `Eligibility check failed`, exit 1. Чтобы повторить сетевую регистрацию и генерацию, использована уже подготовленная отдельная экспериментальная 1.4.5:

```text
SHA-256 ba8a0b179b231f3eb3f17400f06b664d87211679a1c7e04af50f14284d6606d2
```

В этой копии дополнительно пропущены три локальные остановки, как в предыдущем [сравнении версий](auth-version-comparison-2026-11-15.md). OAuth и серверные ответы не подменялись. Запуск использовал тот же свежий вход из keyring; 1.5.9 между новым входом и этими тестами не запускалась в рамках проверки.

Параметры запросов после свежего входа остались теми же:

```text
POST https://daily-cloudcode-pa.googleapis.com/v1internal:loadCodeAssist
{"metadata":{"ideType":"ANTIGRAVITY"}}

POST https://daily-cloudcode-pa.googleapis.com/v1internal:onboardUser
{"tierId":"free-tier","metadata":{"ideType":"ANTIGRAVITY"}}
```

Выбранные поля ответа `onboardUser`:

```json
{
  "code": 403,
  "status": "PERMISSION_DENIED",
  "reason": "UNSUPPORTED_LOCATION",
  "domain": "cloudaicompanion.googleapis.com",
  "error_number": "1008"
}
```

Тело запроса регистрации и её ответ после одинакового редактирования прочих строк совпали с предыдущим тестом 1.4.5 на сессии от новой версии. Затем фактический `POST /v1internal:streamGenerateContent` получил HTTP 403 без ошибки транспорта. Финальный JSON CLI содержит `#3501`, пустой `response`, `num_turns=1` и все счётчики токенов 0.

## Границы вывода

Подтверждены новый обмен кода именно старой версией, вход на прежнем аккаунте, восстановление после перезапуска и тот же серверный отказ бесплатной регистрации. Проверенная гипотеза о влиянии происхождения OAuth-сессии результата не объяснила.

Это не восстанавливает серверное состояние во время прежнего успешного доступа и не различает утрату ранее действовавшего права от изменения серверных правил. Исторические `currentTier/paidTier` остаются UNKNOWN. Бесплатная регистрация текущего аккаунта отклоняется сервером независимо от двух проверенных версий, включая свежий OAuth старой версии.

## Доказательства и состояние

Игнорируемый локальный каталог: `test_cache/auth-version-comparison-2026-11-15/`.

- `fresh-old-oauth-live.json`: аппаратное наблюдение свежего code exchange, token HTTP 200, возврат без ошибки, exit 0;
- `fresh-old-oauth-result.json`: сводка и проверки совпадения параметров;
- `fresh-old-account-comparison.json`: только результат совпадения идентичности без персональных значений;
- `network-1.4.5-baseline-daily-fresh-old-session.json`: повтор обычной 1.4.5 после перезапуска;
- `network-1.4.5-enroll-daily-fresh-old-session.json`: регистрация и генерация на свежей сессии;
- `fresh-old-attempt-1/`: исключённая из сопоставления первого аккаунта попытка.

Во всех окончательных используемых аппаратных трассах `observation_errors=[]`. Установленные бинарники и исходные резервные копии не менялись. В keyring штатно сохранён новый вход прежнего аккаунта. Тестовые процессы завершены. Продуктовый код не изменялся; коммитов и публикации не было.
