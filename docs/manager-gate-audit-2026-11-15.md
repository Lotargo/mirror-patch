# Проверка Manager gate и реальной генерации agy

Дата: 2026-11-15.

## Результат

Свежий Google OAuth успешно завершён штатной командой `agy.exe acp --login` с участием пользователя: процесс сообщил `Logged in` и завершился с кодом 0. После перезапуска Hub возвращает локальный `signed_in`, а идентичность в `GetUserStatus` совпадает с идентичностью завершённого OAuth. При этом получить ответ модели не удалось.

Реальная генерация через Hub (`StartCascade` и `SendUserCascadeMessage`) возвращает серверный `403 PERMISSION_DENIED`, сообщение об отсутствии действующей лицензии продукта, номер `#3501`. Прямой CLI останавливается с `Eligibility check failed`, кодом 1 и нулевым расходом токенов. Установка Manager gate не устраняет эти отказы.

Старый Manager gate по-прежнему однозначно находится и технически накладывается на проверенную сборку 1.5.9. Это подтверждает применимость локальной замены, но не обход серверных ограничений. Утверждать, что вся уязвимость исправлена либо что старый патч предоставляет рабочий доступ, по этим результатам нельзя.

## Аудит записи и статическая проверка

В `source/patcher/utils/atomic.py:86` функция `validate_patch_params` проверяет отрицательные смещения и выход за границы. Если объект имеет `orig`, дополнительно проверяются равенство длин `orig`/`fix` и соответствие исходных байтов. Эти четыре негативные проверки воспроизведены на синтетических данных и отклонены.

У действующего объекта `MANAGER_GATE_X64` поля `orig` нет. Поэтому `apply_patches_to_data` заменяет срез длиной `len(fix)`, но не проверяет ожидаемые исходные байты. Для этой замены размер файла сохраняется. Проверка пересечений отсутствует: синтетические наложенные записи принимаются, последующая запись перекрывает предыдущую. В данном эксперименте применялся один патч к предварительно проверенным байтам, с проверкой хеша и полной неизменности данных вне окна записи.

В текущем Hub-бинарнике API `manager.get_status` вернул `unpatched`. Найдено ровно одно исходное совпадение x64 и ни одного изменённого. Файловое смещение: `0x2b88a0a`, PE VA: `0x142b8940a`. Исходное окно `80 78 08 00 74 3b` заменено на `c6 40 08 01 90 90`. Размер до и после: 231726744 байта. Тестовая копия распознана как `patched`, CLI gate сохранился.

Текущее установленное состояние отличается от исходного `.agybak` ровно четырьмя байтами, по смещениям `0x34443e9`–`0x34443ec`: `80 78 08 00` заменены на `48 85 c0 90`. С окном Manager gate они не пересекаются. Исходный `.agybak` не перезаписывался.

## Что означает статус P0

`source/patcher/status.py` объединяет локальные состояния. `source/patcher/diagnostics.py:73` отдельно учитывает CLI и Hub; для Hub выставляет `unsupported`, не разрешает автоматическое применение и оставляет авторизацию непроверенной. Это согласуется с результатами: наличие локальных маркеров не доказывает доступность модели.

Профиль `source/patcher/hub/profile.py` распознаёт исходный и CLI-only хеши, но не экспериментальный хеш с Manager gate. Он намеренно не расширялся. Для ограниченного эксперимента использовался прямой loopback RPC после проверки точного хеша бинарника, PID, порта и CSRF. Противоречивые поля `AuthResult` по-прежнему не считались успехом.

## OAuth, перезапуск и контроль без Manager gate

Предположение задания о `LoginWithBrowser` не подтвердилось: этот RPC в 1.5.9 возвращает HTTP 500 и `LoginWithBrowser is deprecated and no longer supported`. Обычный `Login` в проверенном запуске `--hub` возвращает HTTP 400 `failed_precondition`: интерактивный auth client для него не инициализирован.

Поэтому свежий OAuth выполнен штатным ACP-входом 1.5.9 с `--app_data_dir=antigravity`. Код введён пользователем и передан ожидающему штатному процессу; в этот отчёт он не включён. Итог: код выхода 0 и сообщение об успешном входе.

Hub перезапущен с тестовым бинарником. Три повторных `GetAuthStatus` вернули согласованный локальный `signed_in`, `hasValidAuth=true`, без failureDetails. `GetUserStatus` вернул профиль того же аккаунта. После отката только Manager gate и нового запуска получены те же три статуса и тот же серверный отказ генерации.

Следовательно, сохранение локального состояния после перезапуска наблюдалось, но причинная связь этого состояния с Manager gate не установлена. Начальный единичный `signed_out`, полученный сразу при старте контрольного Hub до свежего OAuth, нельзя использовать как доказательство эффекта патча.

Запрос: `Reply exactly SERVICE_OK. Do not call tools, read files, or modify anything.` Рабочая директория: отдельный пустой каталог `test_cache/manager-gate-1.5.9-2026-11-15/service-smoke`. Для CLI применены `--print`, `--output-format json`, `--print-timeout 45s`, `--mode plan`, `--disable-slash-commands`.

| Проверка после OAuth | Ответ | Итог |
| --- | --- | --- |

| PATH agy 1.4.5, оба ранее существовавших патча, локальный прокси | `Eligibility check failed`, exit 1 | `num_turns=0`, input/output tokens=0 |
| Hub agy 1.5.9 как CLI, только CLI gate, настройки по умолчанию, локальный прокси | Та же ошибка, exit 1 | `num_turns=0`, input/output tokens=0 |
| Копия 1.5.9 как CLI, оба патча, настройки по умолчанию, локальный прокси | Та же ошибка, exit 1 | `num_turns=0`, input/output tokens=0 |
| 1.5.9 как CLI, профиль `antigravity`, оба патча, локальный прокси | Та же ошибка, exit 1 | input/output tokens=0 |
| Hub 1.5.9, оба патча, `StartCascade` → `SendUserCascadeMessage` | HTTP 403, `PERMISSION_DENIED`, `#3501` | Ответ модели не получен |

Для RPC был указан модельный enum `MODEL_GOOGLE_GEMINI_2_5_FLASH`, возвращаемый самим `GetAvailableModels`; задана конфигурация planner. Создание тестового Cascade прошло с HTTP 200. Отказ 403 получен при фактической генерации, а не при разборе запроса. Дополнительный `GetModelResponse` также вернул 403. Получение списка моделей или пользовательского профиля не учитывалось как успешная генерация.

В журнале прямого CLI наблюдалась последовательность `Print mode: silent auth succeeded`, серверный отказ по лицензии, затем `Print mode: eligibility check failed`. Получение OAuth-токена и разрешение пользоваться моделью оказались разными условиями.

Сначала запрос без явно заданного прокси упирался в TLS handshake timeout. Для последующих запросов использован уже работающий локальный HTTP-прокси `127.0.0.1:10809` через переменные окружения только тестовых процессов. Системные настройки не менялись. Сетевой timeout не трактовался как отказ по лицензии.

## Проверки, состояние и ограничения

- `python -m unittest discover -s tests -v`: 63 теста прошли. Это локальные регрессии диагностики, а не подтверждение доступа к сервису.
- Установленный Hub-бинарник восстановлен до точного хеша перед экспериментом; прежний CLI-патч сохранён. Установка PATH agy не изменялась.
- Исходный `.agybak` сохранён. Тестовые Hub-процессы остановлены. Созданная исключительно для проверки локальная траектория удалена штатным `DeleteCascadeTrajectory`, HTTP 200.
- Продуктовый код патчера в рамках этого эксперимента не изменялся. Ранее существовавшие незакоммиченные изменения не откатывались. Коммитов, push и публикации не выполнялось.
- Новый OAuth выполнен через ACP. Вызов `finalizeLoginAfterValidate` старого language-server auth client динамической трассировкой не подтверждён; интерактивный `Login` в проверенном режиме недоступен.
- Область вывода: конкретные версии, аккаунт и протестированные запуски. Причина серверной классификации лицензии, возможность доступа других аккаунтов и работа полноценного IDE-сеанса не установлены. Наличие 403 не доказывает конкретное изменение защиты между версиями.
