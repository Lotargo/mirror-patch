# Проверка локальных барьеров штатного CLI после OAuth

Дата: 2026-11-15.

## Задача и статус

Проверить утверждение, что старый патч снимал локальную проверку доступности и позволял получать ответы. Исторический результат, сообщённый пользователем, учитывается как исходный контекст и не опровергается текущим отказом.

Для версии 1.5.9 подтверждены два отдельных локальных отказа. На изолированных копиях они последовательно пропущены, после чего штатный CLI создал диалог и отправил пользовательское сообщение своим обычным кодом. Однако ответа модели не получено: CLI вернул `403 #3501`, код выхода 3 и нулевые выходные токены. Цель получить реальный ответ пока не достигнута.

## Почему прежних тестов было недостаточно

`IneligibilityFromResult` формирует описание отказа. Его изменение может убрать текст причины, не меняя состояние `AuthStatus`, по которому другие участки CLI прекращают работу. Поэтому пустое `Eligibility check failed:` не означает, что вся проверка снята.

Вызов генерации через вручную составленные Hub RPC проверял иной вход в backend. Для проверки тезиса о поведении обычного `agy -p` потребовался отдельный эксперимент с нативной цепочкой CLI.

## Два найденных барьера

| Этап | Функция | Наблюдение |
| --- | --- | --- |
| Старт print mode | `printmode.waitForEligibility`, вызов в `printmode.run` | Ошибка прекращает запуск до проверки выбранной модели и отправки сообщения |
| Отправка сообщения | `store.(*Manager).waitForEligibility`, вызов в `SendUserMessage` | Повторная проверка прекращает отправку уже после создания диалога |

Обе проверки обращаются к состоянию eligibility и используют `AuthStatus.EligibilityError`. Их наличие подтверждает, что локальная блокировка в текущем приложении действительно существует.

Экспериментальные копии основаны на чистом официальном 1.5.9 с SHA-256 `8803c289cac04d6e53f2211592d9981c2d5760bc0d9b4a7f222ef6ecc7abb38a`. Изменены только результаты обработки двух локальных отказов в соответствующих точках вызова. OAuth, состояние лицензии на сервере, содержимое сетевых запросов и ответы сервера не подменялись. Эти изменения не добавлялись в продуктовый патчер и не устанавливались в рабочие бинарники.

## Последовательные результаты

| Конфигурация | Результат |
| --- | --- |
| Чистый официальный CLI | `Eligibility check failed` с полной причиной недоступности |
| Копия с пропуском первого отказа | Создан диалог; отправка остановлена второй локальной проверкой |
| Копия с пропуском двух отказов, обычный профиль | Сообщение передано нативным CLI; `num_turns=1`, `response=""`, `403 #3501`, exit 3 |
| Та же копия, чистый профиль, daily endpoint | Тот же результат: один зарегистрированный ход, пустой ответ, HTTP 403 |
| Та же копия, чистый профиль, cloudcode endpoint | Тот же результат: один зарегистрированный ход, пустой ответ, HTTP 403 |

Чистый профиль расположен внутри игнорируемого `test_cache`, не содержит прежних настроек и определений MCP-серверов. `useAiCredits=false`. Стандартный клиент самостоятельно использовал сохранённую OAuth-сессию. В тестовом окружении исключены Cloud/ADC-переменные. Изменение endpoint ограничено окружением одного процесса; фактические origin подтверждены журналами.

Для двух окончательных тестов использована модель, которую текущий CLI выбирает по умолчанию: Gemini 3.8 Flash (Medium). Ранее использованный идентификатор `gemini-3-flash` отсутствует в текущем списке известных моделей CLI. Это выяснилось только после пропуска первого барьера. Следовательно, прежний запуск с этим флагом не подтверждал пригодность модели: он завершался раньше её валидации.

Первый запуск на cloudcode endpoint с обычным профилем завершился таймаутом при подготовке MCP. Он не использован как доказательство серверного отказа. Контроль с чистым профилем устранил этот фактор и получил тот же `403`.

## Что подтверждает журнал

В нативном запуске наблюдались:

1. Успешная тихая авторизация.
2. Создание диалога.
3. `Sending user message to conversation`.
4. Успешное принятие локального `SendUserCascadeMessage`.
5. Ошибка исполнения и итоговый `AGY_ERROR`:

```json
{
  "status": "PERMISSION_DENIED",
  "error_code": 403,
  "code_kind": "http",
  "retryable": false
}
```

Итоговое сообщение содержит `#3501`. CLI зарегистрировал один ход, но расход входных и выходных токенов остался нулевым. Это не подтверждает выполнение модели или получение её ответа.

## Граница доказательства

Подтверждено прохождение двух найденных локальных барьеров и воспроизведение ошибки штатным CLI. Ошибка больше не ограничивается стартовым `Eligibility check failed` или вручную составленным RPC.

На момент проверки обычных журналов точный URL вызова, давшего финальный `403`, не был установлен. Последующая аппаратная трассировка установила `POST /v1internal:streamGenerateContent` → HTTP 403 и прочитала его серверную причину `SUBSCRIPTION_REQUIRED / 1001`. Дополнительно нативная регистрация `free-tier` получила от production-сервера `UNSUPPORTED_LOCATION / 1008`. Метод, контроли и границы доказательства описаны в [сетевом отчёте](native-http-3501-trace-2026-11-15.md).

Дополнительная HTTP/2-трассировка показала только телеметрию, а не искомый вызов. Инструментированные запуски с наблюдением Go HTTP-функции завершались до обычного результата CLI и не использованы как доказательство поведения сервиса. В ходе наблюдения не читались и не сохранялись заголовки авторизации или тела запросов.

Таким образом, тезис «локальная проверка существует и старый патч мог её снимать» совместим с результатами. Тезис «для текущего аккаунта достаточно снять найденные локальные проверки, чтобы получить ответ» в выполненных тестах не подтвердился. Историческая причина прежнего успешного доступа остаётся открытой; точное место текущего сетевого отказа установлено последующей трассировкой.
